## 3. 미리 정리한 핵심 개념

### description과 검증 조건의 차이

`description`은 필드의 의미를 설명하는 정보다. 여기에 “-5부터 +5까지”라고 적는 것만으로 값의 범위가 제한되지는 않는다.

실제 제한에는 다음 조건을 사용한다.

| 설정 | 역할 |
|---|---|
| `Literal["normal", "focused", "completed"]` | 지정한 상태 값만 허용 |
| `ge=-5` | -5 이상 허용 |
| `le=5` | +5 이하 허용 |
| 정수 필드의 `strict=True` | 문자열 `"3"`이나 불리언 `True` 등을 정수로 받아들이지 않음 |

한 번의 예제 상태 점수 변화량을 제한하는 것과 누적 예제 상태 점수의 범위를 제한하는 것은 별개의 작업이다.

### 검증 모델을 별도 파일로 분리하는 이유

`response_validation.py`에 검증 모델을 두면 서버 코드에서 가져와 사용할 수 있다.

```python
from response_validation import LLMResponse
```

이렇게 하면 검증 규칙을 한곳에서 관리하고, LLM을 호출하지 않고도 해당 규칙을 따로 확인하기 쉽다.

단, import만 추가하면 연결이 끝나는 것은 아니다. 기존의 같은 이름의 클래스 정의를 제거하고, 응답 처리 코드가 가져온 모델을 실제로 사용하는지 확인해야 한다.

### JSON 파싱과 응답 검증의 차이

JSON 파싱은 모델이 반환한 텍스트를 Python에서 다룰 수 있는 데이터로 바꾸는 과정이다.

응답 검증은 그 데이터에 필요한 필드가 있는지, 자료형과 값이 정한 조건을 만족하는지 확인하는 과정이다.

예를 들어 상태가 `"angry"`인 응답은 올바른 JSON일 수 있지만, 현재 허용한 상태 목록에는 없으므로 응답 모델 검증에서 거부될 수 있다.

### ValidationError와 기본 응답의 관계

Pydantic 모델을 생성할 때 데이터가 검증 조건을 만족하지 않으면 `ValidationError`가 발생한다.

기본 응답은 Pydantic이 자동으로 만들어 주는 것이 아니다. 서버 코드의 예외 처리에서 직접 반환하도록 구성해야 한다.

기존 코드에서 확인할 흐름은 다음과 같다.

1. LLM 응답을 받는다.
2. JSON으로 파싱한다.
3. `LLMResponse`로 데이터를 검증한다.
4. 검증에 성공하면 정상 응답을 구성한다.
5. 검증에 실패하면 예외 처리에서 기본 응답을 구성한다.

JSON 파싱 실패와 Pydantic 검증 실패는 서로 다른 오류이므로, 각각 어디에서 처리하는지도 확인한다.

### 단독 검증과 API 연동 검증의 차이

| 구분 | 확인할 수 있는 내용 |
|---|---|
| 검증 모듈 단독 실행 | 정해진 입력을 검증 모델이 허용하거나 거부하는지 |
| FastAPI 연동 확인 | 요청 처리 과정에서 검증 모델과 예외 처리가 연결되는지 |
| 실제 Groq 호출 | 외부 모델의 응답을 받아 전체 대화 요청이 처리되는지 |

단독 검증이 성공해도 API 전체가 정상적으로 동작한다고 결론 내릴 수는 없다.
